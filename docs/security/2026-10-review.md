# Security review, October 2026

Ticket: [#48](https://github.com/jperezmart/nest-casl/issues/48), part of #40.

The authorization libraries were attacked from the outside before the release of spec #40: `@jperezmart/casl-core`, `@jperezmart/nest-casl`, `@jperezmart/orpc-casl`, `@jperezmart/next-casl`, `@jperezmart/tanstack-start-casl`, `@jperezmart/hono-casl` and `@jperezmart/casl-react`. The example apps were used only as targets. Demo auth and bugs in CASL itself are out of scope.

## How it was run

The plan was to run the **claude-security** plugin (a multi-agent deep scan with verified patches) over the library packages. **Its scan did not run.** The plugin's pipeline needs the Workflow tool and a cost acknowledgment that the user types, and this audit ran as a session started by another session, without either. So none of its findings are in this report. Every result below comes from attacks tried by hand from the ticket's list: probe scripts against `casl-core` and CASL, reading each Adapter's code, and the example apps' e2e suites.

To add the generic scan, the user starts Claude Code in this repository as the main session and runs `/claude-security`, scoped to the seven packages above.

Each attack that succeeded got a failing regression test first, then the fix, then a changeset, in its own commit. The seams tested are the public interface of each package: `createAbilityFactory`, each Adapter's Rules endpoint and middleware, `createCaslReact`, and the example apps' HTTP API through their e2e suites.

## Findings

| #   | Severity | Finding                                                                             | Status                     |
| --- | -------- | ----------------------------------------------------------------------------------- | -------------------------- |
| 1   | High     | Rule conditions with `undefined` from a missing user field let every record through | Fixed                      |
| 2   | Medium   | No Rules endpoint set `Cache-Control`                                               | Fixed                      |
| 3   | Medium   | Operator injection: a user field that holds an object turns into Mongo operators    | Documented, needs decision |
| 4   | Low      | `casl-react` crashed the render on a malformed Rules endpoint body                  | Fixed                      |
| 5   | Low      | NestJS routes without `@UseAbility` are allowed                                     | By design, needs decision  |
| 6   | Info     | `decide` throws (500) when `detectSubjectType` returns `undefined` or a non-string  | Fails closed, not changed  |
| 7   | Info     | TanStack Start's `denialErrorAdapter` does not check `kind` when deserializing      | Not exploitable            |
| 8   | Info     | Next.js `withDenialPage` trusts any `caslDenial` prop                               | Not exploitable            |

### 1. Undefined conditions let every record through (High, fixed)

**Tried.** A rule `can('update', 'Article', { authorId: user.id })` for a user whose `id` is missing (a JWT without the claim, a `getUser` that maps the wrong field).

**Happened.** CASL keeps `{ authorId: undefined }`. `accessConditions(...).toMongo()` returned it as is. `JSON.stringify` prints `{}`, and the MongoDB driver with `ignoreUndefined`, Mongoose and Prisma drop the field, so the list filter matched every article. The packed rules on the Rules endpoint lost the field too (`["update","Article",{}]`), so the Client ability allowed updating every article. In memory, CASL matched every record without an `authorId`. A `cannot` with an undefined value fails the other way: the record it should have excluded comes back.

**Changed.** `createForUser` checks every rule's conditions, nested operators included, and throws an `UndefinedConditionError` (exported by `casl-core`) that names the action, the subject type and the path (`$or.0.reviewerId`). Every Adapter already answers an error from building the Ability as a 500, never as allowed. Tests: `ability-factory.spec.ts`, "refuses conditions that hold `undefined`". In `nest-casl` this changes behaviour (such a user used to be checked by those conditions), so its changeset is a minor bump (`0.x`). Commit `fix(casl-core): refuse rule conditions that hold undefined…`.

A `null` user field (`{ authorId: null }`) is not refused: in Mongo it is meaningful (no author), and it matches only the records without one.

### 2. No `Cache-Control` on any Rules endpoint (Medium, fixed)

**Tried.** Read the headers of `GET /api/me/abilities` (or the app's own path) on every Adapter.

**Happened.** None set `Cache-Control`. A 200 with no explicit freshness can be cached heuristically, and CDNs set to "cache everything" store it. The response does not vary by cookie, so a shared cache could serve one user's rules (with their id in the conditions) to the next user, and a stale copy could outlive a logout.

**Changed.** `casl-core` exports `RULES_CACHE_CONTROL = 'private, no-store'`. `CaslModule.forRulesEndpoint`, Next.js `rulesEndpoint`, and the Hono and TanStack Start `rulesHandler`s set it on every answer, the 401 included. An oRPC procedure can only set a response header through oRPC's `ResponseHeadersPlugin`, so `rulesProcedure` and `implementRules` set it on `context.resHeaders` when the plugin is there. The four oRPC examples now install it (`backend-orpc`, `backend-orpc-hono`, `next-pages-orpc`, `tanstack-start-orpc`), and the `orpc-casl` README says to. The oRPC 401 is thrown by the middleware before the procedure runs, so it carries no header. A 401 is not heuristically cacheable, so this is acceptable.

Tests: one per Adapter package (Nest e2e, Next, Hono, oRPC), and one in the e2e suite of each oRPC example and of `tanstack-start`. The `tanstack-start` e2e test was written before the fix but first ran after the package had been rebuilt with it, so it was never seen red. Commit `fix: keep every Rules endpoint's answer out of shared caches…`.

### 3. Operator injection through user fields (Medium, documented)

**Tried.** `getUser` returning `{ id: { $ne: null }, roles: ['author'] }`, as a token claim that is an object would.

**Happened.** `{ authorId: user.id }` became `{ authorId: { $ne: null } }`. Both the in-memory check and `toMongo`/`toAst` (`{ operator: 'ne', value: null }`) allowed every article with an author. `{ $exists: true }` behaved the same way.

**Not changed in code.** The library cannot tell an injected object from a deliberate one (`{ authorId: { $in: user.teamIds } }`). The `casl-core` README now warns that values from the user are part of the query, and that `getUser` must check the type of every field it takes from a token or a session. None of the example apps is exposed: `parseUser` only reads string headers. **Decision for the user:** keep this as documentation, or add an opt-in check, for example one that refuses objects in conditions unless their keys are known operators.

### 4. `casl-react` crashed on a malformed body (Low, fixed)

**Tried.** `fetchRules` resolving `{ rules: "x" }`, `{}`, `{ rules: [[]] }`, `{ rules: [{}] }` and `null`.

**Happened.** `unpackRules` threw inside a `useMemo` during render, so the whole tree under `AbilityProvider` unmounted. Nothing was allowed, but the UI went down, and so did `createAbility` (used by `useQueryAbility` and SSR `state`). A proxy's HTML error page served with a 200 already failed earlier, in `response.json()`, and settled as an error.

**Changed.** `AbilityProvider` builds the Ability inside the fetch, so a malformed body settles as a new `MalformedRulesError` in `useAbilityState().error`, and the Client ability allows nothing. `createAbility` allows nothing for a malformed payload rather than throw. Tests: `casl-react.spec.tsx`. Commit `fix(casl-react): allow nothing after a malformed Rules endpoint body…`.

**Left open.** Rules with unknown Mongo operators in their conditions still throw when CASL first evaluates them, during a check rather than while building. Only a server that serves its own broken rules can cause this.

### 5. NestJS routes without `@UseAbility` (Low, by design)

`AccessGuard` allows a route that has no `@UseAbility` metadata, on the handler or its class, whether the guard is applied per controller or globally. Forgetting the decorator therefore leaves a route open. This has always been `nest-casl`'s behaviour, and the other Adapters are opt-in in the same way (a route without the middleware, or a procedure without `.use`). Without the middleware, `assertCan` sees no Ability and answers 401, so those Adapters fail closed. **Decision for the user:** consider a `forRoot({ requireUseAbility: true })` option that denies routes without metadata.

### 6. `decide` with an undetectable subject type (Info)

When `detectSubjectType` returns `undefined`, or an object without a valid `kind` is checked, `decide` throws a `TypeError` while building the forbidden message, or CASL throws on a non-string type. A `detectSubjectType` that throws propagates the same way. Every Adapter answers 500, so this fails closed. Not changed.

### 7. TanStack Start `denialErrorAdapter` (Info)

`fromSerializable` builds `new DenialError(kind, message)` without checking `kind`. A forged payload such as `{ kind: 'admin' }` gives a `DenialError` with that `kind` and status 403. Nothing is executed (seroval decodes the data and only the constructor runs), and forging the payload requires controlling the server's response, which already controls the page. Not changed.

### 8. Next.js `withDenialPage` and the `caslDenial` prop (Info)

A page whose own props contain a `caslDenial` key renders the error page instead of itself. The prop comes from the page's own `getServerSideProps`, never from the request, so an attacker can only trigger this if the app spreads user content into its top-level props. That would show an error page, not reveal anything. Not changed.

## Attacks that failed

- **Subject-type confusion.** Every example checks the stored record, never the request body (`loadArticle`, the subject hooks, `assertCan(…, article)`). Updates copy only `title` and `published` from the body, so `kind` and `authorId` cannot be changed. On a record with `kind: 'all'`, `decide` answers forbidden. CASL's `__caslSubjectType__` is ignored when the app's `detectSubjectType` reads `kind`.
- **Malformed Roles.** A string, an array-like object, `null` or nested arrays count as no Roles. `__proto__`, `constructor`, `toString`, `hasOwnProperty` and `everyone` as foreign Roles grant nothing, because the registry is a `Map` and `everyone` is kept apart. `Admin`, ` admin` and `admin ` are not the Superuser role. Kept as tests in `ability-factory.spec.ts`.
- **A `getUser` that throws or rejects.** Nest, Next (`apiRoute`, `getServerSideProps`, `rulesEndpoint`), oRPC, Hono and TanStack Start (both middlewares and `rulesHandler`) all propagate the error as a 500, and none runs the handler. Kept as tests in `adapter-kit.spec.ts` and `hono-casl.spec.ts`.
- **404 against 403.** On every Adapter, a hidden record and a missing one go through the same code (`notFoundDenial` / `notFound()` / `NotFoundException()` / `ORPCError('NOT_FOUND')` / the router's `notFound()`), so the status, body and headers are the same. The e2e suites already compare the bodies, including TanStack Start's raw server-function answer and the Next.js page. The `onForbidden` hook is never called for not found. A write on an unreadable record answers 404, and a user who may update no article gets the same 403 for every id (ADR 0004). The only difference in timing is a few extra in-memory `can` calls, negligible next to the record lookup both paths make.
- **Allow-all Access conditions.** Without the undefined case (finding 1), a user allowed nothing gets a `NoRecordAllowedError` (403), never `{}`.
- **What the packed rules reveal.** The packed rules hold the user's own id, the condition fields (`published`, `archived`, `authorId`) and the actions. They hold no Role names and no other user's ids. Showing the condition fields is the point of a Client ability.
- **Cross-site reads.** `enableCors()` and Hono's `cors()` answer `Access-Control-Allow-Origin: *` without `Allow-Credentials`, so the browser does not let another site read a credentialed (cookie) response from the Rules endpoint.
- **Middleware ordering.** A Hono route or an oRPC procedure without the Adapter's middleware has no Ability, and `assertCan` answers 401. A middleware that runs after the Adapter's and overwrites `ability` in the context is the app's own code.

## What still needs a decision

1. Operator injection through user fields (finding 3): documentation only, or an opt-in check.
2. NestJS routes without `@UseAbility` (finding 5): keep allowing them, or add an option that denies them.
3. Running the claude-security scan from a main session, to add its generic findings to this review.
